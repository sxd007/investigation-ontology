## DEF-1 [P1] Active Skills 与 manifest 值漂移，无同步机制

### 问题描述

`team-profile.md` 的 `Active Skills` 记录了生成时刻的画像模块快照。此后 `manifests/install-profiles.json` 中 `investigator` 画像扩容，**配置不会同步，且 cold-start 不会提示**。

本环境实测：配置 22 个模块，本机 manifest 26 个，缺失 `data-analysis`、`document-parsing`、`policy-digest`、`investigation-memory`。

后果是功能性的：`investigation-memory` 刚配好 `Memory Write Policy: notify`，`document-parsing` 也配好了 OCR 后端，但两者都不在激活集内。

### 复现与证据

`team-profile.md` mtime = 2026-06-27 11:28。逐提交提取 `manifests/install-profiles.json` 的 `profiles.investigator.modules` 长度：

| commit | 日期 | 模块数 | 变更 |
|---|---|---|---|
| `7953933` | 06-16 | 21 | 初始版本 |
| `236a741` | 06-26 | 22 | 加 ontology |
| `22a8f02` | 06-27 | **22** | 移除 BOM ← 配置生成于此 |
| `c63660c` | 07-23 | 24 | 重构 data-analysis，+2 |
| `1a7c303` | 07-27 | 25 | investigation-memory，+1 |
| `4094478` | 08-28 | 26 | policy-digest，+1 |

配置生成当天 manifest 恰为 22 —— 配置值在当时完全正确，是**事后扩容**造成漂移。

### 根因分析

三层叠加：

1. **合并粒度是"节"不是"值"**。`skills/cold-start/SKILL.md:251` 定义合并流程为"按 H2 节逐节对比"，判断维度只有两条：模板有而配置无的节 → 新配置项；节内仍有 `[PLACEHOLDER]` → 待补全。"角色画像"节存在且 `Active Skills` 有值，两条都不命中。`Active Skills` 属于**行内值漂移**，不在比对维度内。
2. **状态判定绕过了它**。`config-templates/config-loader.md:61` 起：无 `[PLACEHOLDER]`、无中断标记 → 判定 READY → 仅提供 `--redo` / `--check-integrations` / 取消。不走 `--redo` 就永远到不了重写画像的分支。
3. **缺少比对基准**。配置里只存了 `Selected Profile` 和 `Active Skills`，没存 manifest 的版本号或哈希，运行时无法判断快照是否过期。

是否属于"有意设计、画像本就该静态"无法从代码判断，需确认设计意图（见文末"待确认"）。

### 处理建议

**方案 A（推荐，最小改动）** — 在 `SKILL.md:244` 的 4.2 节检测流程中插入一步：

```
3.5 画像模块值漂移检测（新增）:
   - READ <plugin-root>/manifests/install-profiles.json
   - 取配置中 Selected Profile 对应的 modules 列表
   - 与配置的 Active Skills 做集合比对
   - 差异项（新增 / 移除）→ 标记为"画像模块待同步"
   - 展示 diff 后由用户确认是否覆盖（不自动覆盖，避免冲掉手工调整）
```

同时在 4.5 输出摘要的"角色画像"行加一句同步状态。

**方案 B（更省心，但改动大）** — 在 team-profile 的"角色画像"节增加一行 `Profile Manifest Hash`，写入时计算 manifest 内容哈希；升级时比哈希即可，顺带覆盖未来画像改名、删模块的场景。

**本地缓解（用户侧，非修复）** — 手工把 4 个模块名补进 `Active Skills`。

## DEF-2 [P1] ocr-backend 模板注释含 `[PLACEHOLDER]` 字面量，导致状态永久误判

### 问题描述

`config-templates/ocr-backend.md:8` 的 HTML 注释内有一句：

```
每次发版更新此模板时，需要保留所有 [PLACEHOLDER] 标记。
```

这是一句写给维护者的说明，但其中含 `[PLACEHOLDER]` 字面量。cold-start 生成用户配置时是**复制模板 + 填值**（与 team-profile 的"按结构重建"不同），注释被原样保留，于是落到 `{PLUGIN_CONFIG_DIR}/ocr-backend.md`。

而 `config-templates/config-loader.md:61` 与 `:99` 定义的状态判断是：

> 文件包含 `[PLACEHOLDER]`（不区分大小写） → HAS_PLACEHOLDER → 自动进入 cold-start 补全流程

结果：**任何生成过 ocr-backend.md 的用户，该文件会被永久判为 HAS_PLACEHOLDER**。本环境即中招（`~/.codebuddy/plugins/config/efio/ocr-backend.md` 第 8 行），已手工删除注释块临时规避。

补充矛盾点：`config-loader.md:89` 声明 ocr-backend.md 是可选的、"不阻止工作流"，但状态机分支会让 Step 4 走进"自动引导补全"，与"可选"的表述不一致。

### 根因分析

两处独立成因叠加：

1. 模板说明文字与机器可识别的占位符标记**使用了同一个字符串**，无法区分"说明中提到占位符"与"此处是待填占位符"。
2. ocr-backend.md 与 team-profile.md 的**生成方式不一致** —— 前者保留模板头注释，后者不保留（用户版 team-profile 头部无注释，故未中招）。

### 处理建议

三选一，按推荐度排序：

1. **改判断规则（根治）** — 把 `config-loader.md:61/:99` 的"文件包含 `[PLACEHOLDER]`"改为匹配**填充位模式**，例如只认定形如 `**字段名:** [PLACEHOLDER...]` 或 `| 参数 | [PLACEHOLDER...] |` 的行，忽略 HTML 注释块内的出现。
2. **改模板用词（最快）** — 把 `ocr-backend.md:8` 改为不含方括号的写法，如"需要保留所有占位符标记"。一行改动，但 DEF-2 的模式冲突仍在，后续新增类似说明会再次踩坑。
3. **统一生成方式** — 让 ocr-backend.md 的生成也走"按结构重建"，剥离模板头注释。

建议 1 + 2 一起做。

## DEF-4 [P2] VERSION 文件与内容脱节

### 问题描述

本机安装副本 `~/.codebuddy/plugins/marketplaces/https___github_com_sxd007_investigation_ontology/VERSION` 仍为 **1.0.0**，但同目录 `manifests/install-profiles.json` 已含 08-28 提交的 `policy-digest`（26 模块）。源码树 HEAD `ec632f0` 已是 1.1.0。

### 根因分析

VERSION 文件随发布流程手工 bump，与内容提交不同步。今天 `ec632f0 chore(release): bump to 1.1.0 + decouple handbook version from plugin version` 正在解耦 handbook 版本，但 marketplace 安装副本的 VERSION 尚未跟上。

### 影响

依赖 VERSION 做判断的逻辑会失真。本环境的实际后果：cold-start Phase 0 用 `.efio-workspace` 的 `handbook_version: 1.0.0` 与插件 VERSION 1.0.0 比对，得出"手册无需刷新"的结论 —— 前提其实是脏的。

### 处理建议

1. cold-start Phase 0 的"手册是否过期"判断**改为比对内容哈希**而非版本号（模板文件哈希写入 `.efio-workspace`），彻底摆脱 VERSION 同步问题。
2. 若保留版本号方案，则发布流程中校验安装副本 VERSION 与 HEAD 一致。

## DEF-5 [P3] install-profiles.json 路径基准在源码树与安装布局不一致

### 问题描述

`skills/cold-start/SKILL.md:156` 写"读取 `manifests/install-profiles.json`"。该路径相对**安装后插件根**是正确的，但相对**源码树的 skill 所在目录**不存在。

两种布局：

| 布局 | manifests 位置 |
|---|---|
| 源码树 | 仓库根 `cc-investigation-ontology-workbuddy/manifests/`（与 `plugins/` 平级） |
| 安装副本 | 插件根 `.../manifests/`（与 `skills/`、`config-templates/` 同级），**无** `plugins/investigation-ontology/` 这一层 |

### 影响

维护者或 AI 在源码树中按 skill 相对路径定位该文件会找不到（本环境已发生过一次误判，误报为"文件缺失"）。

### 处理建议

在 `SKILL.md:156` 与 `config-loader.md` 的路径表中显式标注基准，例如：

> `manifests/install-profiles.json`（相对于**安装后插件根**；源码树中位于仓库根，安装时拍平到插件根）

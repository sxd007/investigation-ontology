# 制度流程解构方法

本参考将企业制度流程解构方法压缩为执行检查表。它适用于制度、办法、细则、流程、操作规范、授权文件及附件。

## 四层分析

| 层级 | 核心问题 | 主要对象 |
|---|---|---|
| 制度层 | 必须遵守什么 | 原则、红线、责任、奖惩 |
| 管理规则层 | 按什么标准管理 | 条件、权限、额度、时限、标准 |
| 流程层 | 事项如何流转 | 活动、角色、输入、输出、主干与分支 |
| 操作与证据层 | 如何执行和证明 | 系统操作、表单、台账、审批记录、日志 |

## 七步解构

1. 识别文件身份和效力状态。
2. 界定目标、适用对象、场景、触发和排除事项。
3. 用 5W2H 提取核心规则。
4. 用 SIPOC 建立全貌，再按业务时间还原端到端流程。
5. 用 RACI 明确角色、职责和权限。
6. 建立风险、控制、证据和整改闭环。
7. 检查例外、冲突、缺失、断点和不可执行事项。

## 高价值文本信号

- 强制：应当、必须、须、负责。
- 禁止：不得、禁止、严禁。
- 权限：审批、审核、授权、备案、超过。
- 参数：以内、不低于、不高于、工作日、自然日、比例、频次。
- 证据：记录、台账、归档、保存、日志、单据。
- 例外：例外、紧急、补办、退回、驳回、终止、系统故障。
- 效力：发布、生效、废止、替代、解释权、修订。

关键词只用于召回，不用于自动定性。最终分类必须阅读完整句、上下文、定义和附件。

## 规则标准化

优先表达为：

> 当【触发条件】发生时，【责任主体】应在【时限】内，按照【标准】完成【动作】，形成【输出/证据】；未经【批准主体】批准，不得【禁止事项】。

约束：

- 不补写原文没有的主体、时限、阈值或批准条件。
- 一条 Clause 可以产生多个 Obligation，但必须共享同一来源 Clause 锚点。
- 程序细节落流程活动；规范要求保留为 Obligation，两者通过引用关联。
- “尽快”“重大”“必要时”等模糊词保留原文并建立问题记录，不擅自量化。

## 流程还原

先用 SIPOC 回答：输入由谁提供、输入是什么、核心过程是什么、输出是什么、谁接收输出。每个活动至少提取：

- 节点名称、触发条件、责任角色；
- 输入、动作、判断标准、输出；
- 时限、下一节点、条件/异常流向；
- 控制要求、证据和异常处理。

典型主链只作召回提示，不是强制模板：事项触发 → 申请 → 材料审核 → 专业审查 → 权限审批 → 执行 → 验收 → 结算/关闭 → 归档 → 监督。

必须主动寻找退回、驳回、升级、撤销、终止、紧急和补办路径。

## 权责检查

1. 每项活动是否至少一个 R。
2. 每项关键事项是否只有一个 A；多个 A 是否有明确分段边界。
3. 执行人是否有制度授权。
4. 是否自己申请、自己审批。
5. 申请、采购、验收、付款是否过度集中。
6. 临时授权、代理审批、岗位变动和权限回收是否有规则。
7. 制度授权是否与附件权限表一致。

## 风险控制闭环

每项关键控制必须尽量回答：

> 风险是什么 → 谁在何节点执行控制 → 按什么标准判断 → 形成什么证据 → 谁监督 → 发现问题后如何整改。

控制可按时点（预防/检查/纠正）、方式（人工/系统/混合）、频率和重要程度分类。分类必须来自文本或明确标为分析判断。

## 问题分类

- 条款歧义、内容冲突、职责不清、权限缺失；
- 流程断点、时限缺失、例外缺失、证据不足；
- 系统不匹配、上位制度不一致、附件缺失；
- 内容重复、实际不可执行、版本或效力待确认。

问题记录不是本体事实。建议与原文解构分开保存，并注明影响、风险等级、建议和确认责任部门。

## 验收问答

未阅读原文的使用者应能基于成果回答：适用于谁和什么事项、何时启动、谁发起、需要什么材料、经过哪些角色、谁最终批准、权限如何分级、每步时限、禁止事项、例外处理、留痕证据、监督责任、违规后果，以及与实际系统是否一致。

任何答案都必须能跳转到来源锚点；不能回答时应形成待确认项，而不是推测。
